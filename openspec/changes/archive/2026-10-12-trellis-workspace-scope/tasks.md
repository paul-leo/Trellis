## Sandbox e2e results (5.4, 2026-10-12)

Script: `/tmp/trellis-ws-e2e.sh` (bash; throwaway `$SCRATCH` with fake HOME seeded by real `trellis init` + hand-written `managed.yaml` + per-agent presence markers; two fixture git repos; exercises the real `src/cli.ts` entrypoint with HOME redirected). **54/54 checks pass.**

The e2e caught three real bugs, all fixed and pinned by regression tests:

1. **Workspace MCP servers leaked into global user-level files.** `mcp sync`/migrate-cascade inside a workspace rendered repo `.agents/` servers into `~/.codex/config.toml`, `~/.pi/agent/mcp.json`, `~/.claude.json` — a direct violation of the workspace-delivery spec scenario ("global config files are untouched by the workspace entries"). Root cause: the global render consumed merged `canonical.mcp`; `mcpProvenance` had no consumer on the global path. Fix: `WorkspaceLayerInfo.mcpGlobalServers` (pre-merge global map) + `globalLayerMcp()` (src/lib/workspaceMerge.ts), used by every adapter's global render (claude-code, codex, kiro ×2, kimi-code, pi, zcode ×2). Shadowed globals keep rendering globally with their GLOBAL definition (zcode user-first semantics); tombstones do not remove servers from shared user-level files. Regression test: workspaceDelivery.test.ts "global user-level files are untouched by workspace entries; a shadowed global renders with its GLOBAL def". Follow-up: real machines that already leaked get the Trellis-owned workspace entries removed from global files by the next sync's ownership-ledger cleanup.
2. **Rollback false-conflicted on any file written more than once in one backup session.** The planner checked every op against the pre-rollback disk state, so only a multi-written file's LAST write matched; the earlier writes reported "has changed since this run" and exit 1 (the workspace rendered-manifest is rewritten once per adapter per session). The apply phase already restored correctly in reverse write order. Fix: `collectRollbackPlan` now plans newest-first against a per-path simulated state that each planned restore rewinds (src/commands/rollback.ts). Regression tests: rollback.test.ts "plans a file written SEVERAL times in one run as a clean sequential undo" + "restores an OVERWRITTEN file to its pre-run bytes".
3. **Workspace skills leaked into global user-level skill dirs as cross-repo symlinks.** Same root-cause class as #1: global skill symlink delivery consumed merged `canonical.skills`, whose workspace entries carry repo-relative dirs — so `~/.claude/skills/`, `~/.agents/skills/`, `~/.pi/agent/skills/` ended up with symlinks pointing INTO one repo's `.agents/skills/`. This broke exactly the clone/copy scenario: from the cloned root, `sync --check` reported each stale link as "exists as a symlink to …/repo1/.agents/skills/…, not owned by Trellis — left untouched" and exited 1. Found by the closed-loop e2e's clone (`git clone`) and copy (`cp -R`) sections. Fix: `WorkspaceLayerInfo.globalSkills` (pre-merge global list) + `globalLayerSkills()` (src/lib/workspaceMerge.ts), used by all 12 global skill render sites across the six adapters; zcode's Runtime SkillProvider keeps the merged view deliberately (task 2.2). Shadowed globals keep their GLOBAL definitions globally; project-level copies still come from the merged view (workspaceFiles.ts filters `skillProvenance === "workspace"`). Regression test: workspaceDelivery.test.ts "global user-level skill dirs are untouched by workspace entries; a shadowed global still symlinks its GLOBAL def". Follow-up: previously leaked Trellis-owned symlinks in user-level dirs are removed by the next sync's ownership-ledger cleanup.

Final state: 986/986 unit tests, `tsc --noEmit` clean, `npm run build` OK, `openspec validate trellis-workspace-scope --strict` valid, e2e 54/54 — including the closed-loop sections: committed workspace re-attaching after `git clone` AND `cp -R` (4 checks), server removal propagation to rendered files + manifest (6 checks), and migrate → rollback → re-migrate (the loop restarting, 3 checks) — and the run's fake-HOME global files verified clean of every workspace server and workspace skill.

## Multi-project sandbox e2e (follow-up, 2026-10-12)

Script: `/tmp/trellis-ws-e2e-multi.sh` — 7 repos + 2 fake HOMEs, **64/64 checks pass**: (a) two workspaces coexisting under one HOME, each seeing ONLY its own layer (repoA/repoB cross-contamination checks, incl. shared-HOME re-sync no-cross-talk); (b) workspace SHADOWING a global server (project files get the workspace def, user-level files keep the global def, `doctor` names `mcp:figma`); (c) workspace TOMBSTONING a global server (project-local only, `doctor` names `mcp:mailbox`); (d) a plain project with no `.agents/` left completely untouched; (e) workspace discovery from a deep subdirectory; (f) second-machine clone under a DIFFERENT global layer — initial `--check` exit 1 is the fresh machine's OWN globals pending (never repo files), one full render fixes it, and the re-render produces ZERO git diff (committed artifacts are machine-independent); (g) hand-written `.mcp.json` handling: different-name entries are PRESERVED and merged alongside, same-name entries with no manifest record are REFUSED byte-identical, and hand-edits to a Trellis-OWNED entry are converged back (ownership ledger).

This run caught one more real bug (fixed + verified by the e2e itself):

4. **`mcp sync`/`sync` printers dropped conflict remediations.** The unmarked-overwrite guard's plan item carries `remediation` ("run `trellis migrate --workspace` to absorb the existing entry …"), and migrateWorkspace/onboardVerdict printed it — but the mcp.ts and sync.ts report printers rendered only the description, leaving the user at "left untouched" with no next step. Fix: both printers now print `→ <remediation>` for items that carry one (src/commands/mcp.ts, src/commands/sync.ts).

Two earlier "failures" in this run were wrong e2e EXPECTATIONS, not code bugs, and are now pinned as documented behavior: a fresh machine's initial `--check` exits 1 because of that machine's own global layer only; and `mcp add --workspace` cascades a render immediately, so a same-name hand-edit made AFTER the add is drift-converged (repoH), not conflict-guarded (repoG covers the no-manifest case).
