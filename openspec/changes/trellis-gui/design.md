# Design

## Context

See proposal.md - Why. Three facts from the current codebase shape everything below (verified against source, not assumed):

- `agent-trellis`'s public SDK barrel (`src/sdk.ts`) is deliberately read-only — `trellis-sdk`'s existing spec forbids re-exporting anything from `src/commands/*`/`src/adapters/*`. This was a real P5 decision, not an oversight.
- Every mutating command already separates a pure plan-computation function (`collectSyncReport`, `collectMcpAddPlan`, `collectRollbackPlan`, etc.) from a thin CLI-I/O wrapper (`runSync`, etc.) — none of them import `@clack/prompts`; `dryRun` is a real typed option on the plan functions themselves, not CLI-argv-only.
- `src/lib/backup.ts` is the single low-level path every real write goes through today; its own doc comment states the reason it exists is to stop call sites from having to "also remember" to record a backup.

## Goals / Non-Goals

**Goals:**
- A read-write GUI that reuses 100% of the existing write-safety mechanics (confirm, dry-run, backup) — zero new safety logic.
- Ship as an independent package that can iterate and release on its own cadence, without agent-trellis's CLI users installing Rust or a webview toolchain.
- Prove the sidecar architecture end-to-end on one platform before spending effort on cross-platform packaging.

**Non-Goals:**
- Expanding `agent-trellis`'s public SDK barrel. This design finds a path that doesn't require it (Decision 1).
- Windows/Linux distributable builds (Decision 5) — the sidecar/IPC architecture itself is platform-agnostic and this is a packaging-effort deferral, not an architecture limitation.
- A delegated-call timeline view — depends on `trellis-agent-bridge`'s still-unbuilt audit trail (that change's task group 4). This design's data layer doesn't preclude adding it later; it just isn't built now.
- Multi-window, real-time collaborative editing, or any workflow beyond "one operator, one machine, one GUI instance at a time."

## Decisions

**1. `@trellis/gui` lives in this repo as an npm workspace member, and its sidecar imports Trellis's internal command modules directly — not through the public `agent-trellis` package export.**
This is what lets the GUI reuse `collect*Plan`/`apply*Plan`/`src/lib/backup.ts` today, unmodified, while leaving `trellis-sdk`'s existing "SHALL NOT re-export commands" requirement completely intact. The alternative — publish `@trellis/gui` as an independent repo depending on `agent-trellis` via npm, importing only its public barrel — would force expanding that barrel into a stable, versioned, mutating public API before this design is even validated once. Committing to that stability contract before real usage exists is the wrong order of operations; a workspace-internal import can be freely reshaped as the sidecar's real needs become clear, and the public-API question can be revisited later once (if) `@trellis/gui` proves the shape third parties would actually want.
   - *Trade-off accepted*: `@trellis/gui`'s sidecar version is pinned to the `agent-trellis` version in the same repo/commit — it cannot support multiple `agent-trellis` versions the way a properly decoupled SDK consumer could. Acceptable for a first-party tool; revisit if `@trellis/gui` is ever meant to support arbitrary installed Trellis versions.

**2. The sidecar is a persistent local HTTP+WebSocket server, not a per-action CLI subprocess spawn.**
A dashboard needs push updates (file changes, long-running operation progress) that a request/response-only model can't give without polling. The sidecar is a compiled single-file Node binary (`@yao-pkg/pkg` or `bun build --compile`, chosen at implementation time based on which produces the smaller/more reliable binary for the target platform) placed under `src-tauri/binaries/` and registered as a Tauri `externalBin` — spawned by the Rust shell on launch, killed on quit. HTTP handles request/response calls (list views, plan computation, confirm+apply); a WebSocket channel carries push events (file-watcher change notifications, in-progress operation status).
   - *Alternative considered*: stdio pipe instead of HTTP+WS (Tauri natively supports piping a sidecar's stdout/stdin). Rejected for v1 — an HTTP+WS server is easier to develop and debug against directly (curl, browser devtools) during the build-out, and the loopback-only binding (Decision 3) keeps the security posture equivalent to stdio for this single-user, single-machine use case.

**3. Loopback-only binding, no additional auth token for v1.**
The sidecar binds to `127.0.0.1` on a port chosen at startup (OS-assigned ephemeral port, passed to the Tauri frontend via its own launch, not hardcoded) and refuses any non-loopback connection at the socket level. This is the same trust boundary the existing MCP gateway already relies on for local stdio processes — not a new security model being invented.
   - *Risk accepted, not ignored*: any other process running as the same OS user can still reach an ephemeral loopback port (this is a real, known limitation of loopback-only binding, not a hidden one). Mitigation: the port is not written to a predictable, world-discoverable location — it's only known to the Tauri process that spawned this specific sidecar instance — and every mutating endpoint still requires the explicit confirm step (spec: "Mutating operations require explicit confirmation"), so a same-user process reaching the port cannot silently trigger a write without that process also supplying a confirmation the real GUI's dry-run flow produced. A future revision can add a per-launch shared-secret header if this proves insufficient; not needed to ship v1.

**4. Confirmation UX: a modal that renders the same plan object the CLI's dry-run mode computes, with an explicit "Apply" button — no auto-confirm, no "don't ask again."**
Every mutating sidecar endpoint is actually two calls: `POST /plan/<operation>` (pure, side-effect-free, returns the same shape `collect*Plan` already returns) and `POST /apply/<operation>` (requires the plan's own id/hash to have been returned by a `/plan` call first, so a client cannot apply without having fetched a plan in this session). The React modal always shows the plan response before enabling Apply. This mirrors the CLI's own `--dry-run` then real-run two-step, just as two API calls instead of two invocations.

**5. v1 packaging targets macOS only; Windows/Linux are a follow-up, not an architecture change.**
Rust cross-compilation plus per-platform sidecar binary compilation plus (for a real distributable) macOS notarization-equivalent signing on each OS is real, separate effort per platform. Nothing in Decisions 1-4 is macOS-specific — expanding platform coverage later is additive packaging work, not a redesign.

## Risks / Trade-offs

- **[Risk]** The sidecar duplicates onboard's `RunOnboardOptions` resolver callbacks with GUI-native implementations; if `onboard.ts`'s resolver shape changes in a future Trellis change, the GUI's resolvers silently go stale until someone notices a mismatch. → **Mitigation**: since both live in the same workspace/commit (Decision 1), a resolver-shape change is a normal TypeScript compile error in the GUI package, not a silent runtime drift — the same safety a workspace gives any internal consumer.
- **[Risk]** Compiling the Node sidecar to a single-file binary is a less-traveled path than plain `node dist/x.js`; packaging tool bugs (pkg/bun/deno compile edge cases with native addons, dynamic `import()`, etc.) are a real category of failure this repo hasn't hit before. → **Mitigation**: Trellis's own dependency surface is small and pure-ESM with no native addons (confirmed: `@clack/prompts`, `@modelcontextprotocol/sdk`, `yaml` only) — the class of packaging failure that trips up native-addon-heavy projects mostly doesn't apply here. Still budget explicit verification time in tasks before treating packaging as done.
- **[Trade-off]** A loopback HTTP server is a slightly larger attack surface than a pure stdio pipe, in exchange for easier local development. Given the actual mitigations in Decision 3, this is judged acceptable for a single-user desktop tool; revisit if `@trellis/gui` ever needs a materially different threat model (e.g. remote access).
- **[Risk — discovered during task 3.3, fixed during 3.5]** "Every write goes through the existing automatic backup path" (spec requirement) was false for part of the surface this design wires up, and the gap was upstream in `agent-trellis` itself, not introduced by the sidecar. `mcp add`/`mcp remove`/`skill add`/`skill remove`'s own canonical write did not open a backup session — only their cascade-sync sub-step did, and only when that sync had real projected changes to make. Confirmed empirically before the fix: a real `mcp add` followed immediately by `trellis rollback --list` showed zero new backup runs. **Fixed in `agent-trellis` itself** (user decision: "先修然后继续" — fix first, then continue), not worked around in the sidecar: `applyMcpAddWithSync`/`applyMcpRemoveWithSync` (`src/commands/mcp.ts`) and `applySkillAddWithSync`/`applySkillRemoveWithSync` (`src/commands/skill.ts`) now each open their own `openBackupSession` around the direct write when the caller hasn't already supplied one — the exact `manage.ts` pattern this note originally proposed. `skill add`/`skill remove` needed two new `BackupSession` primitives (`createDirFromSource`/`removeDir`, with `dir-create`/`dir-remove` manifest operation kinds in `src/lib/backup.ts`) since directory-level copy/delete had no prior backup primitive — only single-file writes and symlinks did. Verified for real, not just re-reading the code: rebuilt CLI, ran real `mcp add`/`mcp remove`/`skill add`/`skill remove` against a sandboxed home, confirmed each produces a real backup run in `rollback --list`, and confirmed a real `rollback <runId>` genuinely restores `servers.yaml`/the skill directory to its pre-write content. Existing 722-test root suite and the sidecar's own 16-test suite both pass unchanged (behavior-preserving for every caller that already worked). Both the CLI and this sidecar are honest for free, since both call the same fixed functions.
