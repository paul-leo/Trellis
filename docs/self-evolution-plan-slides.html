02 · 调研结论

四个决定性事实:移植可行,且比预想顺利

1

dependencies = []

pyproject.toml 声明运行时零第三方依赖,core 全部只用 Python 标准库 —— TS/Node 全部有直接对应物。这是可行性的决定性证据。

2

Vertex 只是环境变量

core 里没有任何 Google SDK import。LLM 调用 = spawn CLI 子进程 + 注入凭据环境变量。移植时只是换凭据形态。

3

无 Linux-only 代码

全库没有平台 gate。README 的 Linux 是内部环境取舍;Docker 只有 WorkBuddy benchmark 需要 —— 不移植它就不需要 Docker。core 在 macOS 可跑。

4

引擎与 benchmark 彻底分层

依赖方向单向:benchmarks → substrate → core,core 不反向依赖任何东西。引擎可整体移植而完全不碰 Google 的三个 benchmark。

核心移植规模:约 6,000 – 7,000 行 TypeScriptcore ≈ 5,650 行 + substrate 协议 83 行 + config/cli 瘦身移植

06 · 关键机制

四个引擎不变式 —— 移植时必须保真

01

指纹缓存(runmark)在发子进程之前拦

调用键 = _call_fingerprint(label, mission, system, context_dir)。命中即直接返回历史结果,不产生任何模型调用费用 —— 省的是真金白银。

02

穷人沙盒:每次调用独立 mkdtemp + copytree

临时目录销毁前由 harvest 把子路径(如 context/harness)复制回来。无 Docker、无 VM,靠文件系统隔离,macOS 原生成立。

03

失败收口:超时/异常统一为 Reply(ok=false)

重试退避 10s × (attempt-1),失败后循环继续而非崩溃 —— 单个会话失败不拖垮整轮 sweep。

04

judge 预检先行

真跑前先检查 judge 可用:换 judge 模型会被拒绝评分 —— 避免花钱跑完才发现评分链缺失。

08 · 实施路径

移植顺序:按依赖图,每层可独立测试

1

tree → runmark → ledger

零依赖基础层。可编辑树、指纹、预算恒等式 —— 纯数据结构,最先翻译、最先测。

2

spec → prompts

声明层。类型 + 1,163 行 prompt 模板资产(建议原样保留英文,降低移植偏差)。

3

context → library

中间层。穷人沙盒(mkdtemp/copytree → fs 原生)与库管理。

4

proposer → selection

核心层。spawn+env 凭据注入、信号量并发闸、缓存与重试 —— 语义映射最密集处。

5

schedule → recursion → report

编排层。五环循环、树回写/回滚、报表。ThreadPoolExecutor → Promise 并发池。

6

Substrate 接口 + TrellisSubstrate

83 行协议原样翻译;宿主实现:surface 声明树 / materialise 渲染 staging / execute 拉探针会话 / read_trajectory 读会话记录 / preflight = doctor。

7

凭据适配

Vertex env 注入 → 现有凭据形态(agent-bridge 或本机 CLI 登录态)。不移植任何 Google 凭据变量。

8

golden 对照验收

借 harness2 tests/ 的 fixture,Python/TS 双实现同输入比输出 —— 移植正确性的锚。

探针任务集与移植并行建设 —— 先用 fake benchmark 跑通管线,任务集是 execute() 真正有活干的前提

09 · 与 trellis-evolve 草案的映射

旧草案怎么处置:保留 / 改写 / 保留为增量 / 性质改变

✓ 保留

  • D12 穷人沙盒(mkdtemp + copytree)
  • 两段式选择/评分(improver 提案 + judge 评分)
  • 失败收口(Reply(ok=false),循环继续)
  • D13 指纹缓存 · SurfaceSpec 思想
  • 三个刻意偏差:不 bypass 沙盒 / base 留池 / 不绑 Vertex

✎ 改写

  • D2 HostPort 接口倒置 → 作废,改用已验证的 Substrate 5 方法签名
  • 五环等术语 → 对齐 harness2 的 stages 命名
  • "移植方法论,不移植代码"结论 → 修正为"移植引擎"

★ 保留为 Trellis 增量(引擎之外)

  • L1 doctor-oracle 差集 —— harness2 之外的确定性 oracle 验收器,叠在 L4 治理层
  • 分级开启 / 带外批准 —— 产品护栏,不侵入引擎

↻ 性质改变

  • 原 tasks 第 1 组(三个只读前置验证)→ 改为移植前置:先在 fixture 上跑通原版,拿到 golden 基线
