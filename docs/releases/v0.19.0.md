# Trellis v0.19.0

An upstream HTTP MCP server that restarted — or dropped its session store
behind a load balancer — killed the gateway's session permanently. Every
tool call to that server failed with `MCP session no longer exists;
initialize a new session` until the agent session itself was restarted:
the client SDK has no re-initialize path, the gateway never reconnected,
and the registry had no way to swap a fresh client in for the dead one.
Recovery is now automatic, transparent, and confined to the one server.

## Changes

- **Session invalidation is detected, not guessed.** An HTTP error
  response that is not an authentication rejection (anything but
  401/403) whose body mentions a session, or an enveloped protocol
  error with code -32000 and session wording, enters the recovery path.
  The status gate is deliberately "not 401/403" rather than "exactly
  404": the official server SDK answers with 404/-32001 "Session not
  found", but real upstreams answer the same situation with a 400
  carrying `-32000 "MCP session no longer exists"` — real-machine
  verification caught the 404-only gate missing that shape. Auth
  rejections never enter recovery; they remain governed by the v0.18.0
  OAuth behavior.
- **One transparent reconnect, one retry.** The gateway re-establishes
  the session with the same connection logic as startup — OAuth
  credential attachment and header resolution included — swaps the
  fresh client in for all subsequent calls, closes the stale client
  only once the fresh session is serving, and retries the original
  request once. The agent observes nothing. Because session validation
  happens at the HTTP layer before dispatch, the retried request cannot
  double-execute.
- **Single-flight with a cooldown.** Concurrent calls that hit the dead
  session await the same recovery. A recovery failure (or a failed
  retry) starts a 30-second cooldown during which that server's calls
  fail fast instead of reconnect-looping; after the cooldown, the next
  session error triggers recovery again.
- **Status is honest at every step.** A recovering server reports
  `reconnecting`; a failed recovery reports a terminal
  `requiresSessionRestart` state with the `restart the Agent session`
  remediation — no path leaves the server showing a stale `ready`.
- **Errors name their server.** Upstream tool-call failures are wrapped
  with the upstream's name, so a multi-server gateway failure is
  attributable from the error text alone.
- **Tool names may reshuffle after a recovery (known trade-off).**
  Reconnecting re-runs exposed-name allocation for the whole registry;
  a name collision resolved differently can change another server's
  exposed tool name until the next `tools/list`. There is no
  `listChanged` notification in this version.
- stdio upstreams, OAuth 401 refresh/retry, and the v0.18.0
  per-request credential resolution are unchanged and compose with
  recovery: a reconnect inherits the OAuth header path, and a 401 after
  a reconnect still takes the refresh path.

Detection and recovery are pinned by tests against a real client SDK
and a loopback HTTP server that issues and invalidates sessions, and by
a real-machine pass running the built `trellis mcp-runtime` process
against a controllable local upstream: official 404/-32001, custom
-32000 under both 404 and 400, the HTTP-200 protocol-error arm, and
the 403 must-not-reconnect negative all verified in one live gateway.

## Upgrading

CLI: `npm install -g agent-trellis@0.19.0`.

No configuration or stored-credential migration. Running gateways pick
the new behavior up when their agent session starts a new gateway;
already running sessions keep the old behavior until they restart.
